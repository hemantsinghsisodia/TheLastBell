## 2. Code review: `Source/LastBell/Storm/` and the storm part of `Systems/LBConsoleCommands.cpp`

Read in full: `LBStormSubsystem.h/.cpp`, `LBStateLightGroup.h/.cpp`, `LBStormLogic.cpp` (and the param structs of the `.h`), `LBStormSettings.h/.cpp`, `LBStormTypes.h`, `LBStormZone.h/.cpp`, the storm commands in `LBConsoleCommands.cpp`, and the apparition hook in `AI/LBWardenApparition.cpp:304-316`. I did not compile or run anything; this is a read review plus the existing test log.

### Checked and found sound
- **Null and weak-pointer safety.** Every linked light is a `TWeakObjectPtr<ULightComponentBase>` and is skipped when gone (`LBStormSubsystem.cpp:310,334`); zones are weak (`:736`); `CachedWarden` is weak and re-found when stale (`:638-647`); `Settings` is checked before every use in `Tick` (`:779`), `HandleStateChanged` (`:392`) and `RequestFlash` (`:483`); `AddIgnoredActor(Warden)` is only reached when a Warden exists (`:687`, because `ShouldReveal` requires `bWardenExists`); the light, mesh-slot and MID pointers of the light group are weak or null-checked (`LBStateLightGroup.cpp:30,86,190`). Destroyed listeners on the persistent `ULBWorldStateSubsystem` are safe (dynamic delegates are weak), even if `Unbind` finds no game instance in `Deinitialize`.
- **GC.** `Settings` and `Collection` are `UPROPERTY(Transient) TObjectPtr` (`LBStormSubsystem.h:191-195`); the zone box is a `UPROPERTY`; glow MIDs are owned by their mesh component and held weakly; the non-UObject structs hold no raw UObject pointers.
- **Per-frame cost.** The subsystem tick is cheap: intensity step, one Perlin, flash list (normally empty), a 4 Hz exposure sample, a 5 Hz reveal check with the line trace only when every other condition holds (`:679-690`), then `ApplyLights` (returns at once when no flash, `:327`) and the MPC write. A light group ticks only while fading or in Flicker (`LBStateLightGroup.cpp:208-211`); zones never tick. This matches P14-7 (storm cost +0.16 ms mean).
- **Shipping guards.** `lb.Storm.Enabled` and `lb.Storm.Debug` are inside a not-shipping guard (`LBStormSubsystem.cpp:28-47`, `:880-893`); in Shipping `IsStormEnabled()` is a constant true. The `lb.Storm.Flash/Intensity/Freeze` commands are inside the file-wide not-shipping guard (`LBConsoleCommands.cpp:3,256`). **I did not build a Shipping configuration**, so this is by reading only.
- **MPC parameter names.** The 15 name constants (`LBStormSubsystem.cpp:50-64`: 12 scalars, 3 vectors) are the same strings as the list the Monastery test checks against the loaded asset (`LBStormFunctionalTests.cpp:1383-1391`); that test passes in `LBTests_P14_5c.log` (`StormSetup`, Success). The subsystem also logs one warning if a write fails (`:871-875`); that warning is absent from every log I read.
- **Plan rules versus code.** Moon/spot/fill/sky formulas (`:339-354`), writes only while a flash runs plus once at its end (`:327,364`), gap rule (`ScheduledStart`, `LBStormLogic::EarliestStart`), strikes only on `OnStateChanged` add (never from `OnStateReplaced`, `:397,433`), the 5.3 envelope and 5.5 wind formulas, reveal condition order and the trace after the cheap checks, light rule "last present wins", fade with gutter noise, instant apply at BeginPlay and `OnStateReplaced`, glow pairing by nearest light: all as written in the plan.
- **Wind phase wrap.** `WindPhaseWrap` is 100 x 2 pi as a float, about 1.7e-5 rad away from a true multiple of 2 pi; with the 38 cm amplitude that is a step of well under a millimetre, which cannot be seen.

**P3 (none needs a fix before the owner review; each is a note or a small clean-up)**

- **C1. Code defaults are the old wind values; only the asset carries the tuning by the owner.** `LBStormSettings.h:195-216` (`WindBaseHigh` 0.65, `GustHigh` 0.4, `GustFrequency` 0.12, `PhaseSpeedHigh` 2.4) and `LBStormLogic.h:121-127` (`FWindParams`, same four values). The tuned 0.8 / 0.5 / 0.2 / 6.5 live only in `DA_StormSettings`.
  - Failure scenario: someone right-clicks a wind field in the DA and chooses "Reset to Default", or recreates the asset, or a merge drops the asset. The wind silently falls back to the weak values the owner rejected in P14-4 ("plants nearly static"), and no automation test notices (the unit test deliberately uses the struct defaults).
  - Mitigation today: `p14_5_apply.py --check` asserts the four values, so a script run catches it. Cheap fix: update the CDO defaults and the `Logic.Wind` test, or write a comment. (The docs agent is documenting these values as owner-tuned; the code default differs, which the TECHNICAL_DESIGN section should say.)
- **C2. The debug fields on the asset are honoured in Shipping.** `LBStormSubsystem.cpp:377` (`DebugIntensityOverride`) and `:799` (`DebugFreezeFlash`) are not under the not-shipping guard; only the console commands and CVars are.
  - Failure scenario: `DA_StormSettings` is saved with `DebugFreezeFlash` 0.8 (it is dirty in memory right now for exactly this reason). A packaged build then shows a permanent frozen flash and no ambient lightning, with no console to clear it.
  - Mitigation today: `Monastery.StormSetup` and `p14_5_apply.py --check` assert -1. Optional: ignore both fields in Shipping.
- **C3. The MPC is rewritten unconditionally every frame.** `LBStormSubsystem.cpp:849-869`: 12 scalars and 3 vectors are set each tick, including the nine values that only change when the asset is edited. Each `Set*ParameterValue` marks the collection instance for a render-state update, so a uniform buffer upload happens every frame. P14-7 shows the cost within noise (+0.16 ms game thread mean over four pairs), so this is only worth fixing if Phase 18 wants the last fraction of a millisecond.
- **C4. The Warden lookup iterates every actor when no Warden exists.** `LBStormSubsystem.cpp:638-646`: with `CachedWarden` empty (no Warden in the level, or one that was destroyed) the `TActorIterator<ALBWarden>` runs at 5 Hz over the roughly 3000 actors of `L_Monastery`. About 15 000 class checks per second; negligible, but a one-time subscription to the spawn of the Warden would remove it.
- **C5. A pending look gate holds ambient lightning and Warden reveals for up to 90 s.** `LBStormSubsystem.h:111` (`IsFlashBusy` includes `LookWaits`), used by `UpdateAmbient` (`:602`) and `CheckReveal` (`:661`). Scenario: the player enters the courtyard (`CourtyardEntered`) and never looks toward the tower: no ambient flash for the first 90 s. This is the wording of the plan (section 5.3, "ambient not scheduled while a scripted sequence ... is pending") and the run-through of the owner accepted it, so it is a design note only.
- **C6. Misleading activation log.** `LBStormSubsystem.cpp:241` prints "active with 13 linked lights, 0 zones" because the zones register in their own BeginPlay, after `OnWorldBeginPlay` (seen in `TheLastBell.log` at 06:30, 06:39, 06:46 and 07:27 UTC). Cosmetic; `GetZoneCount()` is 7 afterwards (the Monastery test asserts it).
- **C7. A light group is silent on a Static light.** `LBStateLightGroup.cpp:171-184`: `SetIntensity` does nothing on a Static light and the group does not warn. All 62 lights are Movable today (F0). Scenario: a later level edit makes `L_Cl_West` Static; the group stops working with no log line and `StormSetup` still passes.
- **C8. Automation coverage gaps** (searched `LBStormTests.cpp` and `LBStormFunctionalTests.cpp` in `Source/LastBellTests/Tests/` by name):
  - the look-gated strike (`bLookGate`, `LookWaits`, timeout) has no test (no match for `bLookGate`, `LookTarget`, `LookWait`); it is the opening beat;
  - multi-strike sequences (`Count` > 1, `Spacing`, `ProfileOverrides`) and the `TowerTop` and `Finale` triggers have no test; `ScriptedStrikeOnTagOnly` exercises `Ritual.1` only (`LBStormFunctionalTests.cpp:595-680`);
  - `DebugFreezeFlash`, `ConsoleFreeze` and `lb.Storm.Enabled 0` behaviour has no test;
  - `ALBStormZone::ContainsPoint` with a rotated or scaled box, and `GetExposureAt` against the real `L_Monastery` zones, have no test (the P14-3 result already says this; `StormSetup` only counts the 7 zones);
  - the MPC writes of `WindStrength`, `WindPhase` and `PlayerExposure` are not asserted.

  The logic itself is well covered by the 8 `LastBell.Storm.Logic.*` tests; the 8 functional ones cover flash output, story intensity, one scripted strike, reveal, light groups, glow, apparition and the Monastery setup.
- **C9. Materials: two centimetres of margin under the WPO cap.** `M_LB_Foliage` has Max WPO Displacement 40 and `MI_Foliage_GrassMedium02` has amplitude 38; the worst case is 38 x sqrt(1 + 0.25^2) = 39.2 cm at wind strength 1. Raising the grass amplitude to 39 or more would push blades past the bounds extension, and they would clip at the screen edge. The ivy has the same margin (5 against 6). Not a defect now; it is the constraint for any further wind tuning.
