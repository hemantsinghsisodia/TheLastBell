## Major

### M1 (P2): `CP_Approach` is skipped after an unskipped intro

**What happens:**
1. The intro's `!lock:None` is at 27.5 s, but the run stays active until the sequence ends at 29.0 s.
2. In that 1.5 s window the player can walk, but `ALBCheckpoint::CanSaveNow()` refuses ("a cinematic is playing").
3. The checkpoint retries only "while the player stays inside" (`LBCheckpoint.cpp:119-130`).
4. The `CP_Approach` box is 100 cm deep (X -2750 to -2650, `p17_f0_tables.md:423`). A walking player is through it in about 0.5 s, before the run ends.
5. The retry timer clears, and `CP_Approach` never saves. The first save is `CP_Courtyard`, about 8 to 11 s later.

**Evidence (owner sessions):**
- `TheLastBell-backup-2026.11.11-02.34.57.log:2491-2500`: `!lock:None` at 27.50 s, then "Checkpoint 'CP_Approach' refused (a cinematic is playing)", then "Intro finished (finished)", then the next save is `SaveCheckpoint 'CP_Courtyard'`.
- `TheLastBell-backup-2026.11.11-07.37.49.log:2536-2544`: the same sequence.
- When the intro is skipped, the run ends together with the unlock, and `CP_Approach` saves (same log, `02.34.57.log:2682`).
- The P17-6 Results entry (plan, line 1018) records this as "refused ..., then the next checkpoint saved normally". That is this defect, read as a pass.

**What the docs say instead:**
- "`CP_Approach` saves on the first steps after the intro": `TECHNICAL_DESIGN.md:665`, plan 2.7 (line 253) and the comment at `LBCheckpoint.cpp:78`.

**Impact:**
- Between the spawn and `CP_Courtyard` there is no save. Quitting there leaves no Continue.
- A death there runs `HandlePlayerDeath` -> `NewGame` (`LBGameMode.cpp:48-54`). That replays the intro, which contradicts GAME_DESIGN:37 ("a death reload never plays it").
- No hazard in the approach is known, so the practical risk is low. It is still a reproducible save-path defect.

**Repro (PIE on `L_Monastery`, `lb.Cine.Enabled 1`, `lb.Cine.Rate 1`, no save):**
1. Start PIE.
2. Do not skip the intro.
3. Hold W from the moment the cards end, so you move as soon as the lock lifts at 27.5 s.
4. Keep walking toward the gate.
5. The log shows `CP_Approach` refused and never `SaveCheckpoint 'CP_Approach'`.
6. Stop before the courtyard. `lb.Checkpoint.Load` reports "no valid save".

**Suggested fix (any one of these; the lead picks):**
- (a) Move the intro's `!lock:None` to the last frame, or end the run when the lock goes `None` at the tail.
- (b) Make the cinematic subsystem broadcast `OnCinematicFinished`, and have refused checkpoints retry once on it even if the player has left the box (the save transform is the checkpoint's own arrow).
- (c) Let checkpoints save while `IsPlaying()` and the lock is `None`.

Add a functional test for "refused during a cinematic, then saved after it", and correct the P17-6 Results line.

### m3 (P3): Pausing during a cinematic (Phase 18 risk)

**Evidence:**
- `ULBCinematicSubsystem` does not override `IsTickableWhenPaused` (default false), so markers, cards, credits, the skip hold, the mark and the look all freeze under a world pause.
- `ULBAudioSubsystem` ticks while paused (`LBAudioSubsystem.h:158`).
- I have not verified here whether the `ULevelSequencePlayer`, its camera, its 2D music sections and its fades pause with the world.
- If the sequence keeps running under a pause, the markers it crosses fire in a burst on unpause (`MarkersToFire` from `PrevSeconds`), and the cards and credits drift from the picture. If it pauses, the cinematic music needs the same treatment.

**Status:** no pause exists today (the ending no longer pauses, plan 2.7). So this is only a risk, and R-77 part 2 covers just the bell.

**Suggested fix (Phase 18):** either block the pause menu while `IsPlaying()`, or pause the sequence player and the subsystem together, then test both. Add it to R-77 or a new risk.
